# 开发前 UI 规格

首次组件实现先建立完整适用规格；局部修改只补受影响行并关联旧基线。取证是设计事实，目标是采用的画面，技术映射是实现决定，三者不能相互覆盖。

## 规格形成

1. 复用来源证据、页面和原子树；按选定组件/资产边界组织条目，维护 source node → componentId → rowId。
2. 读取 [参数与状态契约](references/spec-contract.md)，记录实际值、原始单位、采用值/计算规则、坐标系、视口/状态、依据、未知项。不能只写“与设计一致”。
3. 字体、效果、裁切、透明留白及独立双端资产在实现前取证；已烘焙效果不二次叠加。行为与输入/配置契约单独记录并关联。
4. 输出可供审阅的原值/目标/差异表和覆盖清单。没有完整来源不能报 100%。原始值、目标和提取/决策/实现/验证状态分列。
5. 有结构化需求时使用 [合成规格示例](assets/ui-spec.example.json) 的字段；现有等价格式直接复用。Review 从同一数据派生，不在表格中维护另一套值。

## 进入实现的条件

采用目标可来自用户指定且核实无冲突的设计、现有有效决定或有依据的常规工程映射；不逐属性重复审批。未回答的布局/展示模式、核心交互、关键数据对象及破坏兼容的决定不能默认为接受，阻断相应范围，其余已知部分可以实施。

非关键缺口可标 assumption 并说明影响和下一步；不能标 adopted 或通过，不能宣称完整还原。临时功能预览与完整视觉验收分开。先写效果代码再反填目标、用实现常量生成验收期望均不可接受。

变化按来源更新、取证修正、新需求或实现缺陷分类；保留旧基线，更新相关 row/断言/测试。交给 [实现](../dtc-implementation/SKILL.md) 和 [视觉验证](../dtc-visual-validation/SKILL.md)，本阶段不报告实现或测试通过。
