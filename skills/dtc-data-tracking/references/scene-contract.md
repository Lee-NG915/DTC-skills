# 场景方案、验收与交付

先确定请求是新业务链路、已有场景补点、契约缺陷修复或只读分析可行性。复杂度按语义判断：一个按钮也可能涉及跨页关联、成功判定或标准电商事件所有者。小补点不一按钮一文档，既有有效 Review 不重复要求。

## 场景卡

沿用项目同主题记录，至少说明：业务目标、统计对象/单位、触发与排除、字段来源/类型、数据许可、过滤/分母/时间窗、去重/关联、目的地映射、验证与明确非目标。新链路在生产实施前完成项目要求的开发 Review；记录真实审核来源和版本，助手自查不是开发人员批准。

从用户准备看的行列反推字段和目标看板。规划事件标为规划，不混入已启用清单；优先复用适合的现有事件，不为每个场景重建 producer。一个事件可以服务多个场景，变更反查所有消费者、字段映射和分析覆盖。场景重叠时不能直接相加，也不能把独立事件强行拼成必经漏斗。

区分事件有效必需字段和某分析所需字段；缺字段要明确降级，不填假值。公共 context 与业务 Builder 分工明确，不重复注入同一字段。位置按已确认的可见顺序取值，隐藏槽不无意占号；排除条件应有会在错误实现下失败的独立断言。

## 实施和验证

按已确认范围修改 producer、契约、Builder、adapter 和映射。标准电商事件核对唯一 owner；不顺带接管 checkout、服务器或别的应用。上报失败不阻塞业务，不额外发业务请求，不等待 analytics 而延迟跳转。

新增场景由实施者接入实际测试注册/发现机制，同步场景和引用；不建空测试充数。用列表及实际执行结果核对所选用例存在且运行。正常/排除/缺字段、许可允许/拒绝/未知/撤回、不补发、重复初始化和下游失败按实际契约覆盖。公共 runtime 或构建依赖变化扩大到真实消费者并重建，即使入口未启用。

## 可执行的 AI 验收说明

需要重复浏览器验收时，在同场景维护独立的验收 SOP，链接业务规则及适用候选。每个 case 写：目标环境与前置状态、定位依据、动作、等待上限、预期/不应发生、证据、停止/恢复条件。README 面向业务，平台配置指南写配置，SOP 写动作，避免三份重复步骤。

SOP 是说明，不是授权或自动 DSL。项目有固定平台执行器时使用其登记、冻结绑定和回执机制；不从临时目录写旁路脚本逃避门禁。没有适配器时标缺能力，不能照抄来源工程的 CLI、伪造 run 或将手动观察称作机器完成。

## 分层交付

分别记录设计、实现、本地测试、指定部署、标签触发、下游接收、处理后查询/报表、业务验收、发布。queued、模拟请求或调试视图只证明对应层。点击不证明到达，HTTP 成功不证明界面更新，已有事件通过不证明新分析链路打通。

完成交接提供场景文档/SOP、已核实配置或证据链接、整体报告。区分完整场景、限定配置和诊断承诺，能力受阻时不静默缩小目标。报告说明每层事实、缺项、最后候选、下一动作和责任；没有调度回执不承诺后台继续。

当前状态更新到同一权威记录，历史失败保留；不把旧通过加新增未跑用例写成当前全部通过。只有原目标与验收真实满足才写完成。
