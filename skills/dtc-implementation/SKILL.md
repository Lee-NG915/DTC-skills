# 页面与组件实现

## 按目标档案实现

先消费 `dtc-context` 输出的 `targetProfile`。使用其中规定的源码目录、组件伴随文件、
状态管理、预览入口和命令；若目标档案要求组件文档、测试或 stories，必须与实现同一
patch 交付。不要把来源项目的 Liquid section、Theme Editor schema、平台对象或构建
命令直接复制到目标项目。

## 开始前

复用上下文、技术方案及页面/原子组件树。首次 UI 实现必须先有 [UI 规格](../dtc-ui-spec/SKILL.md) 的适用目标；局部改动补受影响行。非 UI 功能可不适用视觉阶段。有歧义的展示模式先取得决定，其余独立区域继续；不把建议值默认为用户批准。

按 [实现与预览契约](references/production-preview.md) 核对真实源码、调用方、依赖及运行时入口。已有代码是实现证据，不自动成为新的业务规则。

## 实施顺序

1. 对照原子/组合契约实现输入、状态、输出和资源边界。依赖自下而上可复用，页面按真实数据/导航连接；不要求无收益的额外层。
2. 根据 UI row 映射布局、字体、效果、双端素材和内容，依据采用目标而非凭印象反填规格。效果先查是否已烘焙入素材。
3. 数据适配独立：有数据、空结果、失败、延迟、预览 fixture 按实际能力处理；预览数据不能流入生产。
4. 按项目机制实现事件、生命周期和清理、受控状态、异步竞争/恢复、输入语义与实例隔离。保持旧配置/输入兼容及相关消费者行为。
5. 生产输入/依赖/加载链变化后构建；验证最终资源解析和运行结果。开发服务器的隐式转译不能掩盖生产缺依赖。
6. 建立消费真实组件及同一参数契约的场景预览，提供已核实的可访问入口和复现方式。环境不支持则说明缺口，不能只给假定端口。

## 验证与修正

把候选交给 [组件测试](../dtc-component-testing/SKILL.md) 和 [视觉验证](../dtc-visual-validation/SKILL.md)。视觉、参数、场景可共用证据，按类别分别报告，不强制顺序跑三遍。最小修正后只复跑受影响项，旧失败保留历史。

已稳定复现的逻辑缺陷优先取得目标规则的修复前失败再改；实现已完成不得补造 RED。纯样式无需新增逻辑单测。涉及优化使用 [优化流程](../dtc-optimization/SKILL.md)，不把修复原契约偏差和新增优化混为一谈。

交接给 [通用交付](../dtc-delivery/SKILL.md)，代码、预览、实际运行与用户接受分别记录。
