# Nx 按能力适配

适用于已经采用 Nx 的项目。版本、包管理器、插件、目标均从当前仓库读取；以下命令示例使用 npm，其他工程换成其实际包管理器前缀。优先使用已有官方 Nx 技能及工具；本文件独立总结工作流，不复制供应商技能或 CI 执行器。

## 探索与任务

- 先查 lockfile 和 Nx 版本，再用 `npm exec nx -- show projects`、`npm exec nx -- show project <project> --json` 读取解析后的项目/目标；不能只从 project.json 判断推断目标是否存在。
- 用已有 targets 执行 `npm exec nx -- run <project>:<target>`。多项目/affected 的基线、参数和依赖范围先核对实际帮助与项目图，不猜 flags，不把全部项目当默认范围。
- 图展示消费者/依赖，任务结果分别记录命令、退出码、实际用例和缓存来源；缓存命中不能证明真实远端环境通过。

## 新建结构与插件

新增应用、包或项目结构时，先发现已安装的生成器和选项；按当前版本帮助运行 dry-run，审阅将写入的文件再执行。插件缺失时先确认是否确需安装及兼容版本，不为了运行示例擅自升级工作区。优先仓库生成器，遵循其同步和目录规则。

## 工作区包链接

无法解析内部包时先检查包的真实 name、package manager workspace 范围、消费方声明和实际导出；用包管理器支持的工作区依赖机制连接。不要用路径 alias、随意复制源码或直接深层导入来掩盖缺失的包依赖。重建相关包并验证消费方；不要混用 lockfile 或安装器。

## 导入项目

导入前固定源版本，确认未提交文件如何处理、目标子目录、包名冲突、包管理器、历史保留需求及清理范围。读取该版本 Nx 导入功能与框架插件支持情况；不猜存在某个命令。

在隔离目录试导入，检查框架/插件版本、脚本与推断 target 重复、根配置、TS project references、lint/test 工具、样式与生成文件规则。先让导入项目的原能力通过，再验证目标仓库消费者；不替其他项目升级依赖或全局覆写配置以消除局部冲突。迁移记录区分旧仓历史事实与新仓实测。

## CI

CI 监控交给 [dtc-ci-monitor](../../dtc-ci-monitor/SKILL.md)，绑定当前提交/attempt。Nx Cloud、自动修复、MCP 和 subagent 均是可选环境能力，不是技能包自带能力；未提供时使用现有只读 CI 工具并说明缺口。

官方入口：[命令参考](https://nx.dev/docs/reference/nx-commands)、[项目配置](https://nx.dev/docs/reference/project-configuration)。执行前以安装版本的帮助为准。
