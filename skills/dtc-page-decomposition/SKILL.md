# 页面组件拆分

页面拆分回答“页面由哪些可独立理解和验证的区域组成”，不直接把每个 Figma frame 或 group 变成代码组件。先明确页面目标、进入方式、主要用户任务、响应式范围和页面状态。

## 拆分步骤

1. **标记页面区域**：按布局边界、内容责任、状态变化、数据来源和复用机会标记 header、导航、主内容、列表/网格、详情、辅助区域、反馈/错误和 footer 等区域。名称使用业务职责，不使用只在设计稿里出现的图层名。
2. **建立页面树**：输出 Page → Region → Composite Component → Atomic Component 的候选树，并标记每个节点是已存在、待复用、需组合还是需新建。页面树表达组合关系，不替代原始 Figma 节点树。
3. **确认边界**：一个节点适合拆分的信号是独立数据、独立状态、独立响应式行为、复用机会、可单独测试或需要隔离维护。只因视觉上被框起来、名称相似或层级较深，不足以新建组件。
4. **记录跨区关系**：说明共享数据、事件、URL/导航、筛选/分页、加载/错误/空状态和跨区域联动。避免让页面组件直接承担所有数据请求、展示细节和全局状态。
5. **输出状态矩阵**：为页面和关键区域记录 loading、success、empty、error、partial、permission/offline（适用时）、mobile/desktop、交互前后和恢复路径。

## 拆分决策

每个候选节点写职责、非目标、输入/输出、拥有的状态、依赖、消费者、复用方式和不拆分理由。页面级组件负责组合和页面语义；可复用展示逻辑、数据适配和交互状态交给更窄的组件或适配层。跨框架输出概念树和契约，不写某个框架或渲染器的特定实现假设。

页面拆分必须和 [dtc-atomic-decomposition](../dtc-atomic-decomposition/SKILL.md) 衔接：页面树确定组合关系后，再拆某个复杂组件内部的原子边界。涉及视觉数值时交给 [dtc-ui-spec](../dtc-ui-spec/SKILL.md)；涉及依赖、SSR/CSR、状态管理或接口选型时交给 [dtc-technical-design](../dtc-technical-design/SKILL.md)。

## 可交接产物

实施拆分时读取 [契约与记录](references/decomposition-record.md)，将组件 ID、状态所有权和来源映射写入现有技术稿。已有边界直接沿用；新高影响边界才澄清。
