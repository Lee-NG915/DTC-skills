# 需求分析

复用已有目标和范围；缺少上下文时使用 [dtc-context](../dtc-context/SKILL.md)。将输入整理为：问题、受影响对象、期望结果、本次范围、非目标、约束、依赖和可观察验收标准。按行为影响选择记录粒度：短变更记录、一页任务、完整需求或故障恢复记录。

每条结论标为 `已确认`、`建议`、`待确认` 或 `未知`。每轮只追问影响最大的 1–3 个问题，优先确认对象、边界、核心规则和失败恢复。不要要求业务人员回答代码、数据库或平台内部问题；技术可行性留给实现阶段。

验收标准覆盖正常、边界、异常和恢复，使用“在……情况下，当……时，应……”描述。区分功能是否正确和上线后效果是否改善。用户说“继续”“出稿”不等于需求方确认；没有确认时保持草稿状态。

输出需求记录和下游影响，交给 [dtc-design-evidence](../dtc-design-evidence/SKILL.md) 或 [dtc-implementation](../dtc-implementation/SKILL.md)。同一需求持续更新一份记录，不为方案、实施、修复和复盘重复建档。
