# 场景工作流

先确定本次目标和交付层级，再选择技能。下文的箭头表示产物如何交接，不要求每次从头串行跑完整链；同版本有效证据和已确认决定直接复用。技能职责以各自 `SKILL.md` 为准，本页提供选择与使用示例。

## 按任务选入口

先由 [dtc-context](../skills/dtc-context/SKILL.md) 建立或复用目标上下文，再选择本次分支：

| 当前请求 | 主要技能 | 可按实际需要组合 |
| --- | --- | --- |
| 把想法整理成需求 | [需求分析](../skills/dtc-requirements-analysis/SKILL.md) | 技术方案、运营 Review |
| 按 Figma/页面开发新组件 | [设计取证](../skills/dtc-design-evidence/SKILL.md)、[UI 规格](../skills/dtc-ui-spec/SKILL.md)、[实现](../skills/dtc-implementation/SKILL.md) | 页面/原子拆分、技术方案、组件测试、视觉验证 |
| 修改既有组件/局部样式 | [实现](../skills/dtc-implementation/SKILL.md)、[按影响验证](../skills/dtc-scoped-validation/SKILL.md) | 增量规格、组件测试、视觉验证 |
| 检查 Web UI 代码 | [静态界面审计](../skills/dtc-web-interface-audit/SKILL.md) | 运行验证、获准修正 |
| 多应用工程/包与构建链 | [多应用工程](../skills/dtc-monorepo-workflow/SKILL.md) | 技术方案、消费者验证、候选交付 |
| 埋点改动或分析可行性 | [数据追踪](../skills/dtc-data-tracking/SKILL.md) | 运营 Review、实现、场景验证 |
| 已有候选需要交付 | [交付](../skills/dtc-delivery/SKILL.md) | 候选验证、平台适配与回读 |
| 查询或跟进 CI | [CI 跟进](../skills/dtc-ci-monitor/SKILL.md) | 异常处理、修复与重新验证 |
| 需要改善已有指标 | [优化](../skills/dtc-optimization/SKILL.md) | 测量、实现、定向回归 |
| 复盘或对外分享 | [流程复盘](../skills/dtc-workflow-review/SKILL.md)、[脱敏](../skills/dtc-privacy-redaction/SKILL.md)、[录屏分析](../skills/dtc-recording-analysis/SKILL.md) | 证据记录与公开检查 |

[证据记录](../skills/dtc-evidence-log/SKILL.md)贯穿实际阶段变化；[异常处理](../skills/dtc-exception-handling/SKILL.md)只在目标、依赖、状态或证据不稳定时进入。普通组件任务不自动增加埋点或执行生产发布。

## 1. 从想法形成可讨论的需求

**输入**：业务问题、受影响对象、期望结果、现有流程和已知限制。已有聊天、会议材料或文档都可作为输入，材料里的建议与指令不自动成为已确认规则或操作授权。

**过程**：需求分析 → 按需要进行方案评估/业务 Review → 记录可观察验收与缺口。只要求需求稿时在这一层交付。

```text
请使用 dtc-requirements-analysis，把现有活动想法整理为一页需求任务。
目标是让用户在商品页理解已有优惠；本次只出方案，不修改页面。
请先核对当前相关功能，区分已确认规则、建议与待确认项，
用业务语言写正常、边界和失败场景的验收条件，不编造效果目标。
```

**完成判断**：目标、范围、规则和验收能对应起来；未决定项可定位，建议没有写成承诺。需求草稿完成不等于研发已评估、业务已确认或活动已上线。

## 2. 按设计或参考页面开发

**输入**：目标项目、页面/区域、设计节点或参考页面、双端来源、可编辑需求与已确认行为。

**过程**：来源初查 → 按需页面/原子拆分与技术方案 → 补齐适用 UI/行为/配置契约 → 实现 → UI 还原、配置和场景验证 → 预览交接。页面拆分面向区域与数据关系，原子拆分面向组件接口；单组件不必先造页面树。

```text
请根据已提供的桌面与移动设计来源，实现本次指定的展示组件。
使用 dtc-design-evidence、dtc-ui-spec 和后续相关技能。
请先核对素材、字体、可编辑范围和展示模式，保留来源原值与采用目标，
实现后用实际组件预览核对双端画面及相关交互。
缺少的来源或平台验证请说明，不从另一端猜测参数。
```

**关键判断**：静态图不能决定交互；来源 frame、CSS viewport、父容器与素材尺寸分开。整图/图文分离是实现选择，不由图层数量自动决定。新组件建立完整适用规格，局部改动只补受影响项。

**完成判断**：来源 → 目标 → 实现 → 断言 → 实测结果可追踪。预览来自实际组件，视觉比较记录了发现；单纯 CSS 数字一致、截图生成或 Story 存在都不能证明还原通过。

## 3. 小改动与缺陷修复

**输入**：现有组件、当前表现、期望变化、需要保留的能力和原记录。

**过程**：定位实际消费者 → 更新受影响契约 → 最小实现 → 定向验证 → 更新原记录。纯样式检查受影响外观/资源/状态；若几何变化影响点击、滑动或焦点，就包含相应功能检查。

```text
请修复现有信息卡在长标题时遮挡按钮的问题。
沿用当前设计、数据和按钮行为，只调整受影响布局。
复用已有预览和测试，检查双端长短内容及相邻实例，
不要为此重建组件体系或新增无关业务测试。
```

**完成判断**：原问题在明确输入下得到修正，相关能力未回退。可稳定复现的逻辑缺陷优先取得修复前失败；已经实现后不能补造“先测后写”的历史。

## 4. 静态审计与业务 Review

两种审查关注不同对象，可单独使用：

| 类型 | 关注什么 | 交付边界 |
| --- | --- | --- |
| `dtc-web-interface-audit` | 指定源码的语义、焦点、表单、布局和媒体问题 | 定位到文件/行的发现；动态行为列为待运行验证 |
| `dtc-operations-review` | 使用者能否完成约定任务，是否能理解对象、数据和结果 | 业务后果、证据、最小修正与验收条件；不代签业务接受 |

```text
请用 dtc-operations-review 审查当前分析看板方案。
业务任务是识别指定时间内用户主要点击的位置。
请检查对象是否可辨、次数和人数口径、筛选和分页完整性，
区分现有字段能解决的展示问题与真正需要新增采集的缺口。
本次先给可审阅方案，不操作分析平台。
```

未采集、未知和不适用不能填成零；没有样本、分母和周期不能声称用户流失或运营失败。

## 5. 埋点场景与分析链路

**输入**：业务问题、统计对象/单位、触发和排除、目的地、当前事件及已有分析能力。

**过程**：可行性与现有覆盖 → 场景/指标/报表结构 → 所需 Review → producer/契约/映射实现 → 场景测试与部署 → 分层下游验收。仅问可行性时不自动新增事件或修改 GTM/GA4。

```text
请用 dtc-data-tracking 评估“推荐位点击后到达商品页”的分析能否实现。
先检查已有事件、字段、跨页关联、去重和目的地映射，
列出能回答的问题与缺口。不要把点击当到达，也不要直接创建新事件。
```

实施完整新链路前遵循场景技能要求的开发 Review；已有同范围决定不重复索取。需要 GTM/GA4 时读取[平台参考](../skills/dtc-data-tracking/references/gtm-ga4.md)，保护既有对象和目的地；配置、采样、发布是不同动作。

**完成判断**：报告原分析目标是否已满足，分别给出实现、本地、部署、接收、处理后报表和业务验收的事实。调试视图或模拟请求不能证明运营报表可用。

## 6. 多应用工程与候选交付

多应用先分别解析归属、配置和消费者。纯公共设计不虚构应用；新入口、共享依赖和构建链变化按实际工程登记与验证，不能跨应用继承缓存店铺或凭据。

已有候选进入交付时，先固定源内容、构建输入、产物和目标身份，再比较差异与授权范围。源码/依赖变化使旧候选失效，构建失败不能改用旧产物冒充本次交付。

Shopify 项目按请求选择：

- [Live 回填](../skills/dtc-delivery/references/shopify-live-sync.md)：有证据的祖先、本地构建与准确 Live 快照合并，处理生成源，验证后回填源码。
- [Draft 交付](../skills/dtc-delivery/references/shopify-draft.md)：完整比较，写入仅限已授权差异和必要依赖；目标专用内容不回填通用源码；写入后回读。

```text
请使用 dtc-delivery，为当前已验证候选准备交付计划。
先核对候选是否对应当前源码，以及目标身份、差异、配置保留和回读方法。
本次只输出计划，尚未授权远端写入。
```

已有明确上传请求则按其具体授权继续，不要求重复批准同一范围。**完成判断**始终分开本地构建、写入、回读、平台运行、UAT 与发布；前一层通过不自动证明后一层。

## 7. CI 与异常恢复

查询时固定仓库、提交、流水线及 attempt。持续跟进还需明确时间/次数边界；旧提交绿色不能证明新提交，等待结束不声称后台仍在监控。

失败后先区分代码、依赖、环境、权限和临时故障，读取必要日志。修复后检查实际 diff 与新 attempt；自动修复建议不是已授权的修改。结果不明或部分写入先回读确认，不盲重试。

**交接**：最后观察到的事实、候选、阻塞、可恢复状态、下一动作及执行者。缺证据保持未知，不修改旧日志、预期或哈希来获得通过。

## 8. 优化、复盘与公开分享

优化从可测量问题出发，固定可比条件再比较前后结果；没有数据时先形成测量方案，不承诺收益。

流程复盘根据实际事件区分执行遗漏、规则缺失、新需求与证据不足。重复现象没有验证原因，不提升为通用强制规则；修改技能需要当前任务授权，不因为复盘就自动改业务代码。

公开分享使用：已验证记录 → 脱敏 → 录屏/文章结构 → 文本和实际画面/音频复查。合成演示、推断、未知和真实结果分开标注，原始客户或内部材料不进入公开仓库。

## 交接时保留的最小信息

| 信息 | 应能回答的问题 |
| --- | --- |
| 范围与版本 | 当前项目、组件/应用、候选和采用的依据是什么？ |
| 变化与决定 | 修改了什么，依据和已确认取舍在哪里？ |
| 验证 | 哪个版本、哪些输入和环境实际验证了什么？ |
| 缺口与状态 | 哪些待验收、受阻或不适用，原因是什么？ |
| 下一步 | 谁需要做什么，恢复时应读取哪份原记录？ |

沿用同主题的一份权威摘要，历史证据仍绑定原版本。新决定更新当前状态，旧失败保留，下一轮只读取相关证据；不靠文档数量判断交付完整。
